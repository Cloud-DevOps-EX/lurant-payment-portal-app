# Payment Portal — Terraform + GitHub Actions CI/CD

End-to-end pipeline that provisions all AWS infrastructure for the payment
portal — networking, an RDS PostgreSQL database, and a Lambda + API Gateway
application tier — and deploys the application itself, all through Terraform.
GitHub Actions drives validation, security scanning, plan, and (after manual
approval) apply.

Single environment for now (`prod`), AWS only, no application code beyond a
placeholder Lambda used to prove the pipeline end to end.

## Architecture

```
GitHub Actions (OIDC, no static AWS keys)
        │
        ▼
   Terraform (infra/)
        │
   ┌────┴─────────────────────────────────────────┐
   │                                                │
   ▼                                                ▼
VPC (2 AZs)                                  S3 (Lambda artifacts, versioned)
 ├─ public subnets + NAT                            │
 └─ private subnets                                 │ CI uploads app.zip
     ├─ RDS PostgreSQL (private, encrypted) ◄────┐   │
     │     KMS CMK, Secrets Manager creds        │   │
     └─ Lambda (VPC-attached) ────────────────────┘◄──┘
              │  reads DB creds from Secrets Manager
              ▼
        API Gateway (HTTP API)
              │
        WAFv2 (managed rules + rate limit)
              │
         public internet
```

## Repo layout

```
bootstrap/            One-time, applied manually. State backend + OIDC role.
infra/                Everything else — applied by CI.
  modules/
    network/            VPC, subnets, NAT, security groups
    database/            RDS Postgres, KMS, Secrets Manager
    artifact_store/      S3 bucket for the Lambda deployment zip
    lambda_api/           Lambda, API Gateway, WAF, IAM
app/src/              Placeholder Lambda (GET /health, GET /db-check)
scripts/              package_lambda.sh — builds the deployment zip
.github/workflows/    CI/CD pipeline
```

## 1. Bootstrap (one-time, manual)

This step cannot run in CI — the pipeline needs a state backend and an IAM
role to exist before it can authenticate or store state.

```bash
cd bootstrap
terraform init
terraform apply \
  -var="github_org=<your-github-org>" \
  -var="github_repo=<your-repo-name>" \
  -var="aws_region=us-east-1"
```

Save the outputs — they feed GitHub repo configuration in step 2:

```bash
terraform output
# state_bucket_name
# lock_table_name
# github_actions_role_arn
```

If your AWS account already has a GitHub OIDC provider for
`token.actions.githubusercontent.com` (only one is allowed per account), add
`-var="create_oidc_provider=false" -var="existing_oidc_provider_arn=<arn>"`.

## 2. GitHub repository configuration

Under **Settings → Secrets and variables → Actions → Variables**, add:

| Variable | Value |
|---|---|
| `AWS_REGION` | e.g. `us-east-1` |
| `AWS_ROLE_ARN` | `github_actions_role_arn` output from bootstrap |
| `TF_STATE_BUCKET` | `state_bucket_name` output from bootstrap |
| `TF_LOCK_TABLE` | `lock_table_name` output from bootstrap |

No AWS secrets are needed — auth is via OIDC.

Under **Settings → Environments**, create an environment named `production`
with at least one required reviewer. This is the manual approval gate before
`terraform apply` runs against real infrastructure.

## 3. First run

Push to `main` (or open a PR first to review the plan comment, then merge).
The pipeline:

1. **validate** — `terraform fmt`, `terraform validate`, `tflint`
2. **security-scan** — `checkov` against `infra/` (see `.checkov.yaml` for
   the documented, deliberate skip list)
3. **build-artifact** *(push to `main` only)* — creates the artifact S3
   bucket if it doesn't exist yet, packages the placeholder Lambda, uploads
   it, captures the S3 object version
4. **plan** — `terraform plan`, posted as a PR comment on pull requests
5. **apply** *(push to `main` only, requires the `production` environment
   approval)* — `terraform apply` against the exact reviewed plan

After the first successful apply:

```bash
cd infra
terraform init -backend-config="bucket=<...>" -backend-config="key=payment-portal/terraform.tfstate" \
  -backend-config="region=<...>" -backend-config="dynamodb_table=<...>"
terraform output api_endpoint
```

```bash
curl https://<api_endpoint>/health     # {"status": "ok"}
curl https://<api_endpoint>/db-check   # {"status": "ok", "db": "reachable"}
```

## Security baseline included

- No static AWS credentials anywhere — GitHub OIDC → scoped IAM role
- RDS: private subnets only, `publicly_accessible = false`, storage
  encrypted with a customer-managed KMS key, TLS enforced (`rds.force_ssl`)
- DB credentials generated by Terraform and stored only in Secrets Manager;
  Lambda's IAM role can read exactly that one secret and decrypt it with
  exactly that one KMS key
- Security group chain: internet → API Gateway/WAF → Lambda (VPC) →
  `lambda_sg` → `db_sg` (5432 from `lambda_sg` only) — no public ingress
  anywhere near the database
- WAFv2 on the public API: AWS managed Common + SQLi rule groups, plus a
  per-IP rate limit
- Terraform state: versioned + encrypted S3 bucket, DynamoDB lock, TLS-only
  bucket policy
- `checkov` gate in CI on every plan/apply

## Explicitly out of scope (do before this touches real cardholder data)

- Multi-environment promotion (dev → staging → prod) — add via a per-env
  `-var-file` and a separate state key; the module structure already
  supports it
- Blue/green or canary Lambda deploys (CodeDeploy) — currently a direct
  Terraform-managed update
- Full PCI-DSS program controls: CloudTrail org trail, GuardDuty, AWS
  Config, WAF log shipping to a SIEM, formal network segmentation review,
  Secrets Manager automatic rotation

## Teardown

```bash
cd infra
terraform destroy   # set db_skip_final_snapshot=false beforehand if you want a final RDS snapshot kept

cd ../bootstrap
terraform destroy   # only after infra/ is fully destroyed — this removes the state bucket/lock table
```
